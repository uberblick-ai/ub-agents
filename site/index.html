ub-agents

An autonomous coding loop for GitHub.

Any agent, no server.

brew install uberblick-ai/tap/ub-agents

macOS or Linux. You need git, an authenticated gh, and the agent CLIs you want to run.

What is ub-agents?

Your agents prepare issues, implement them, review the pull requests and merge what passes. When a decision needs a person, they raise a hand and wait. You define the roles and rules; ub-agents handles the handoffs.

It is for engineers and teams of up to a few dozen people with a hacker, hands-on mentality: full control, without a convoluted setup or cloud infrastructure to run.

Under the hood, it is a glorified script that polls labels and calls an agent. You could write one in an afternoon. This project is for everything after that afternoon: duplicate claims, interrupted runs, endless review loops, comments from strangers and GitHub failures. Browse our closed issues to see what it took.

The handoffs

Labels are the queue. A launcher runs the agent whose label matches each issue or pull request, and the agent's outcome moves the labels on to the next role. ub-agents init sets up this starter workflow:

needs-preparation  issue-preparer  → ready, or needs-human to ask
ready              implementer     → a pull request with needs-review
needs-review       reviewer        → ready-to-merge, or needs-changes → implementer
ready-to-merge     integrator      → merged, or needs-human for a maintainer

Each role is a few lines of YAML, with instructions that live in your repository:

implementer:
  runtime: "codex:gpt-6.1-sol:high"
  trigger: [ready, needs-changes]
  outcomes:
    handed-off: {add: [needs-review]}
  instructions: .agents/implementer.md
  worktree: true

Rename a label, drop a role or add one; the launcher follows the file. Agents' retros show where the instructions fall short, so you fix them once instead of in every chat. That is loop engineering.

A real run

On 19 October, a user reported that ub-agents launch rejected an origin that used an SSH host alias (#597). Once the issue was labelled needs-preparation, the loop took it from there (UTC):

14:19  issue-preparer  claude  found the issue small and clear, marked it ready
14:21  implementer     codex   changed 7 files, ran 2,109 tests, opened #598
14:33  reviewer        claude  reviewed against the acceptance criteria, approved
14:38  integrator      claude  confirmed CI and the merge policy
14:41  #598 merged, #597 closed 🎉

Twenty-two minutes from the first agent to the merge, with no person in between. Each step is a comment on the issue and the pull request, and a restarted launcher rebuilds its state from them. That is why there is nothing to host.

Before you run it

You need:

  • A Mac or Linux machine with your agent CLIs signed in: a laptop, or an always-on server for overnight runs.
  • A GitHub account for the launcher with write access. We recommend a dedicated account, not an admin.
  • The checks that gate a merge, such as your CI.
# run in your local checkout
$ ub-agents init
$ ub-agents launch

init opens a setup pull request with the starter roles, instructions and merge policy. Review the permissions, merge it and launch. Your merge policy decides what the loop merges and what waits for a maintainer; the FAQ covers trust, cost and the rest. To add capacity, start another launcher on any machine. They all share one queue.
