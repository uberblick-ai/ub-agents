ub-agents

An autonomous coding loop for GitHub.

Any agent, no server.

brew install uberblick-ai/tap/ub-agents

macOS or Linux. You need git, an authenticated gh, and the agent CLIs you want to run.

What is ub-agents?

Your agents prepare issues, implement them, review the pull requests and send work back when it needs fixing. When a decision needs a person, they raise a hand and wait. You define the roles and rules; ub-agents handles the handoffs.

It is for engineers and teams of up to a few dozen people with a hacker, hands-on mentality: full control, without a convoluted setup or cloud infrastructure to run.

Under the hood, ub-agents is a glorified script that polls labels and calls an agent. You could write the first version in an afternoon. The rest is handling duplicate claims, interrupted runs, endless review loops, comments from strangers and GitHub failures. That is the part this project is for. Feel free to browse our closed issues to see what it took.

The handoffs

Labels are the queue. You start a launcher, and it runs the agent whose label matches each issue or pull request. When the agent finishes, its outcome moves the labels on to the next role. ub-agents init sets up this starter workflow:

needs-preparation  issue-preparer  → ready, or needs-human to ask
ready              implementer     → a pull request with needs-review
needs-review       reviewer        → ready-to-merge, or needs-changes → implementer
ready-to-merge     integrator      → merged, or needs-human for a maintainer

Each role is a few lines of YAML. It names a CLI such as claude or codex, a model, and instructions that live in your repository:

implementer:
  runtime: "codex:gpt-6.1-sol:high"
  trigger: [ready, needs-changes]
  outcomes:
    handed-off: {add: [needs-review]}
  instructions: .agents/implementer.md
  worktree: true

Rename a label, drop a role or add one; the launcher follows the file. After a run, agents report missing context, unclear rules and avoidable rework. Use their retros to fix the instructions once instead of repeating the same correction in every chat. That is loop engineering. Every key has a short page in the configuration docs.

A real run

On 19 October, a user reported that ub-agents launch rejected their origin because it used an SSH host alias, which people with two GitHub accounts use to pick a key (#597). Once the issue was labelled needs-preparation, the loop took it from there (times in UTC):

14:19  issue-preparer  claude  found the issue small and clear, marked it ready
14:21  implementer     codex   changed 7 files, ran 2,109 tests, opened #598
14:33  reviewer        claude  reviewed against the acceptance criteria, approved
14:38  integrator      claude  confirmed CI and the merge policy
14:41  #598 merged, #597 closed 🎉

Twenty-two minutes from the first agent to the merge, with no person in between. Each step is a comment on the issue and the pull request: who ran, on which model, and what it reported. A restarted launcher rebuilds its state from those comments. That is why there is no database and nothing to host.

Before you run it

You provide the machine, the accounts and the rules:

  • A Mac or Linux machine with git, an authenticated gh and your agent CLIs signed in. A laptop runs the loop while it is awake; an always-on server keeps it going overnight.
  • A GitHub account for the launcher with write access to the repository. We recommend a dedicated account, not an admin.
  • The checks that gate a merge, such as your CI, and a merge policy that says which changes wait for a maintainer.

Agents run on your machine with the access you configure. Review their permissions before launching. Work happens on branches, and your merge policy determines which changes need a maintainer. Outside issues and pull requests wait for authorization under the approval rules. When an agent needs a decision, it marks the item needs-human and asks.

$ cd your-project
$ ub-agents init     # opens the setup wizard; review before Apply
$ ub-agents launch   # runs the loop; q stops after the current run

init shows every change before applying it. Review the starter instructions and merge policy, merge them, and launch from a clean default-branch checkout. More capacity is one more ub-agents launch, on a teammate's laptop or a server; every launcher shares the same queue. See installation and add more launchers.
